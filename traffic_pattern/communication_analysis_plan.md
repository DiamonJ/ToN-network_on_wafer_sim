# LAMMPS MPI 通信特征分析计划

## 一、实验目标

使用 LAMMPS + DUMPI 收集不同条件下的 MPI 通信 trace，分析以下通信特征：

1. **MPI 操作占比分布** — 各 MPI 操作（ALLREDUCE、BARRIER、SEND/RECV、BCAST 等）在总通信中的占比
2. **Rank 间通信热点图** — 任意两个 rank 之间的通信量/通信次数矩阵
3. **通信-计算比例** — 不同条件下通信时间 vs 计算时间的变化趋势
4. **扩展性分析** — 随 rank 数增多，通信特征如何变化（强扩展）

## 四、分析内容

### 4.1 每项实验的输出分析

| 分析项 | 方法 | 产出 |
|--------|------|------|
| **操作占比** | 从 dumpi2ascii 输出或 CCDG 解析各 MPI 调用类型计数 | 饼图/堆叠柱状图 |
| **通信热点图** | 跨 rank 边按 (src_rank, dst_rank) 聚合通信量 | 热力图矩阵 |
| **通信-计算比** | CCDG 中 compute_cycles vs 通信事件数 | 比例折线图 |
| **通信量分布** | 每条跨 rank 边的 bytes 统计 | 分布直方图 |
| **集合操作分解** | ALLREDUCE/BARRIER/BCAST 各占比例 | 柱状图 |

### 4.2 跨维度对比分析

| 对比维度 | 分析内容 | 图类型 |
|---------|---------|--------|
| **原子规模 vs 通信特征** | 相同 rank 数下，增大原子数的影响 | 多线折线图 |
| **Rank 数 vs 通信特征** | 相同原子数下，增加 rank 的影响 | 多线折线图 |
| **体系间对比** | Same 原子数+rank，不同势函数的影响 | 分组柱状图 |
| **强扩展性** | 原子数固定，rank 数增加时通信占比变化 | 双轴图 |

## 五、所需工具开发

### 5.1 新测试用例生成

创建 `cases/` 下的子目录和 `in.lammps` 文件：

- `cases/lj_0.1k/in.lammps` — 3×3×3 FCC (~108 atoms)
- `cases/lj_1k/in.lammps` — 7×7×7 FCC (~1,372 atoms)
- `cases/lj_10k/in.lammps` — 14×14×14 FCC (~10,976 atoms)
- `cases/eam_cu_1k/in.lammps` — EAM 铜 (7×7×7)
- `cases/lj_mix_1k/in.lammps` — LJ 双组分 (7×7×7)

### 5.2 批量 Trace 捕获脚本

基于已有 `run_trace_capture.sh`，扩展为批量运行脚本 `batch_trace_capture.sh`，支持：

- 遍历所有用例目录
- 遍历所有 rank 数
- 自动命名输出目录 `runs/{体系}_{原子数}_{rank}r_{时间戳}`
- 汇总生成 trace 清单

### 5.3 通信特征分析脚本

新建 Python 分析脚本 `analyze_communication.py`，功能：

1. 解析 DUMPI 二进制 trace（通过调用 `dumpi2ascii`）
2. 提取通信事件序列
3. 统计 MPI 操作占比
4. 构建 rank-rank 通信矩阵
5. 输出 JSON 统计数据
6. 生成可视化图表（matplotlib + seaborn）

### 5.4 CCDG 解析扩展

在已有 `dumpi2ccdg` 基础上，可选增加：
- 打印更详细的 MPI 操作统计
- 支持输出格式化的通信统计摘要

## 八、假设与风险

| 风险 | 缓解措施 |
|------|---------|
| EAM 势文件获取困难 | 使用 LJ 体系作为备份，先完成所有 LJ 实验 |
| 运行时间过长（10k 原子 + 32 ranks） | 先用 100 步快速扫描，选关键配置跑 500 步 |
| 0.1k 原子 + 32 ranks 通信开销过大 | 属于极端情况，分析时可单独标注；若跑不动可跳过 |
| 系统上已存在的 EAM 势文件路径未知 | 先用 `find /work1 -name "*.eam"` 或 `*.eam.fs` 搜索 |

## 九、验证方法

每项实验执行后检查：

1. **Trace 完整性**：`dumpi-*.meta` 文件是否存在，且各 rank 都有对应的文件
2. **CCDG 正确性**：节点数合理，无明显的 send-recv 不匹配
3. **数据一致性**：总发送字节数 = 总接收字节数
4. **结果合理性**：随 rank 数增加，通信占比单调递增
